# AgentForge ReAct 层06、会话记忆扩展：窗口会话记忆设计与实现思路

> 适用版本：release_1.x
> 适用模块：`agentforge-framework/agentforge-agent-core`
> 源码位置：`agent/extend/memory/window`
> 维护者：长路

**核心理念：窗口会话记忆的一切设计，最终都围绕 `maxMessages`（最大会话窗口记录条数）展开——用固定的消息条数上限控制进入模型上下文的规模，超过上限后按规则淘汰最早的消息。**

系列定位：本文属于「AgentForge 核心模块设计原理文章系列 / 02、通用 ReAct Agent 层」，是会话记忆专题的第 02 篇。上一篇定下了 `ChatMemory / ChatMemoryProvider / ChatMemoryStore` 三层契约，本篇只讲其中一种策略实现——**窗口会话记忆**。

一句话结论：

> **窗口记忆不存消息，只负责裁剪；每次读写都委托给 `ChatMemoryStore`，一次批量 `add` 只做一次读、一次裁剪、一次写。**

<br/>

## 一、为什么需要窗口

模型上下文不能无限增长。一方面，主流模型的上下文窗口有硬上限；另一方面，消息越多，token 成本越高、响应越慢，早期无关信息还会干扰模型判断。

最直接的控制方式就是**只保留最近若干条消息**：

```text
maxMessages = 6

System, U1, A1, U2, A2, U3, A3
                ↓ 淘汰最早的对话
System, U2, A2, U3, A3
```

但“删最早的一条”并没有看起来那么简单，有两个必须处理的例外：

1. **系统消息不能删**：它是 Agent 的行为约束，删掉后模型可能立刻跑偏；
2. **工具调用不能拆散**：`AiMessage` 里的 `toolExecutionRequests` 与紧随其后的 `ToolExecutionResultMessage` 是一组，只删其中一个就会产生孤儿消息。

窗口记忆就是围绕这两个例外构建的裁剪策略。

<br/>

## 二、职责边界：只做策略，不做存储

`MessageWindowChatMemory` 的定位非常克制：

| 职责 | 是否负责 | 说明 |
|---|---|---|
| 保存消息 | 否 | 状态全部放在 `ChatMemoryStore` |
| 窗口裁剪 | 是 | 超过 `maxMessages` 时按规则淘汰 |
| 系统消息常驻 | 是 | 淘汰时跳过第 0 条系统消息 |
| 工具消息成组淘汰 | 是 | 删除工具调用时连带删除对应结果 |
| 持久化介质 | 否 | 由注入的 Store 决定，内存/MySQL/Redis 均可 |

类里只有三个字段（`MessageWindowChatMemory.java:31`）：

```java
private final Object id;
private final int maxMessages;
private final ChatMemoryStore store;
```

**重点**：它自身没有任何 `List<ChatMessage>` 状态。消息永远在 Store 里，窗口只在读出来之后、写回去之前做一次加工。这样做的好处是：换存储不需要改裁剪规则，改裁剪也不会影响存储实现。

<br/>

## 三、核心实现思路

### 3.1、状态外置：每次读写都走 Store

```java
@Override
public synchronized List<ChatMessage> messages() {
    List<ChatMessage> messages = new LinkedList<ChatMessage>(store.getMessages(id));
    ensureCapacity(messages);
    return Collections.unmodifiableList(new ArrayList<ChatMessage>(messages));
}

@Override
public synchronized void clear() {
    store.deleteMessages(id);
}
```

`messages()` 不只是简单转发，它会在返回前再裁一次。原因是 Store 里的数据可能由旧版本写入、或由外部直接更新，读时裁剪可以保证任何情况下交给模型的消息都不超过窗口上限。

### 3.2、批量 add：一次读、一次裁剪、一次写

窗口记忆提供了批量写入重载（`MessageWindowChatMemory.java:55`），这是它和“逐条追加”实现最大的差别：

```java
public synchronized void add(ChatMessage... newMessages) {
    if (newMessages == null || newMessages.length == 0) {
        return;
    }
    List<ChatMessage> currentMessages = store.getMessages(id);
    List<ChatMessage> allMessages = new LinkedList<ChatMessage>(currentMessages);

    for (ChatMessage message : newMessages) {
        if (message == null) {
            continue;
        }
        // 系统消息替换逻辑
        allMessages.add(message);
    }

    ensureCapacity(allMessages);
    store.updateMessages(id, allMessages);
}
```

执行流程可以概括为：

```text
store.getMessages(id)
        ↓
合并本轮新消息（处理系统消息替换）
        ↓
ensureCapacity 裁剪
        ↓
store.updateMessages(id, allMessages)
```

**为什么强调批量？** 如果每来一条消息就调用一次 `add`，接入 MySQL 后每条消息都会触发一次查询加一次更新。一次 ReAct 轮次里，用户消息、AI 回复、多条工具结果加起来可能有五六条，批量写能把 N 次往返压缩成 1 次。

单条 `add(ChatMessage)` 只是批量版本的语法糖：

```java
@Override
public void add(ChatMessage message) {
    add(new ChatMessage[] {message});
}
```

### 3.3、系统消息：替换，而不是追加

系统消息在窗口里是“唯一且常驻”的。写入时的处理逻辑是：

```java
if (message.type() == ChatMessageType.SYSTEM) {
    int existingSystem = firstSystemIndex(allMessages);
    if (existingSystem >= 0) {
        if (allMessages.get(existingSystem).equals(message)) {
            continue;
        }
        allMessages.remove(existingSystem);
    }
}
allMessages.add(message);
```

三种情况：

| 场景 | 行为 |
|---|---|
| 窗口里没有系统消息 | 直接追加 |
| 已有系统消息且内容相同 | 跳过，避免重复 |
| 已有系统消息但内容不同 | 先移除旧的，再追加新的 |

这样既保证了系统消息只有一条，也允许配置更新后新提示词覆盖旧提示词。

### 3.4、工具消息：成组淘汰

裁剪发生在 `ensureCapacity`（`MessageWindowChatMemory.java:106`）：

```java
private void ensureCapacity(List<ChatMessage> messages) {
    while (messages.size() > maxMessages) {
        int messageToEvictIndex =
                !messages.isEmpty() && messages.get(0).type() == ChatMessageType.SYSTEM ? 1 : 0;
        if (messageToEvictIndex >= messages.size()) {
            return;
        }
        ChatMessage evicted = messages.remove(messageToEvictIndex);

        if (evicted instanceof AiMessage && ((AiMessage) evicted).hasToolExecutionRequests()) {
            while (messages.size() > messageToEvictIndex
                    && messages.get(messageToEvictIndex).type()
                            == ChatMessageType.TOOL_EXECUTION_RESULT) {
                messages.remove(messageToEvictIndex);
            }
        }
    }
}
```

两个关键点：

1. **淘汰起点**：如果第 0 条是系统消息，从索引 1 开始淘汰，系统消息永远不动；
2. **成组删除**：淘汰带工具调用的 `AiMessage` 后，循环删除紧跟在它后面的 `ToolExecutionResultMessage`，直到遇到非工具结果消息为止。

**注意**：这里只处理“AI 工具调用 + 紧随其后的结果”这种标准结构。如果工具结果被其他消息穿插，说明消息写入顺序本身有问题，不应该由窗口记忆来兜底。

### 3.5、Provider：同会话复用，共享 Store

`MessageWindowChatMemoryProvider`（`MessageWindowChatMemoryProvider.java:16`）做两件事：

```java
private final int maxMessages;
private final ChatMemoryStore store;
private final Map<Object, ChatMemory> memories = new ConcurrentHashMap<Object, ChatMemory>();

@Override
public ChatMemory get(Object memoryId) {
    ChatMemory memory = memories.get(memoryId);
    if (memory == null) {
        memory = MessageWindowChatMemory.builder()
                .id(memoryId)
                .maxMessages(maxMessages)
                .chatMemoryStore(store)
                .build();
        ChatMemory previous = memories.putIfAbsent(memoryId, memory);
        if (previous != null) {
            memory = previous;
        }
    }
    return memory;
}
```

- **同会话复用**：`putIfAbsent` 保证并发下同一 `memoryId` 只产生一个记忆实例；
- **共享 Store**：所有记忆实例注入同一个 Store，因此换存储只需要在 Provider 构造时换一个实现。

**注意**：Map 里缓存的是“记忆对象”，不是“消息内容”。所以它不会随对话变长而膨胀，只随会话数量增长；长期运行的服务仍需要配合会话过期策略清理。

## 四、一次 add 的完整流程

以“系统消息更新 + AI 回复 + 工具结果 + 用户追问”为例：

```text
初始：System(old), U1, A1(tool call), T1, A2

add(System(new), U2)
  ├─ 读取：System(old), U1, A1, T1, A2
  ├─ 替换系统消息：System(new), U1, A1, T1, A2
  ├─ 追加用户消息：System(new), U1, A1, T1, A2, U2
  ├─ 裁剪：若超过 maxMessages，从索引 1 开始淘汰
  │        淘汰 A1 时，T1 一并删除
  └─ 写回：store.updateMessages(id, 最终列表)
```

整个过程中，`MessageWindowChatMemory` 只在内存里操作一份临时列表，完成后整段覆盖回 Store。

<br/>

## 五、接入方式

默认使用进程内存储：

```java
ChatMemoryProvider provider = new MessageWindowChatMemoryProvider(100);
```

需要持久化时，传入自定义 Store：

```java
ChatMemoryStore store = new MysqlChatMemoryStore(agentMemoryMapper);
ChatMemoryProvider provider = new MessageWindowChatMemoryProvider(100, store);
```

再交给 Agent：

```java
ReActAgent agent = ReActAgent.builder()
        .chatModel(chatModel)
        .chatMemoryProvider(provider)
        .toolService(toolService)
        .build();
```

在 `agentforge-service` 中，窗口参数通过配置解析，`WindowChatMemoryProviderFactoryExtension` 读取 `maxMessage` 后创建 Provider，未配置时默认 `1000`。

## 六、边界与后续

当前实现刻意保持简单，已知边界如下：

1. **同实例串行**：`add` / `messages` / `clear` 都加了 `synchronized`，但只保证单实例内的原子性。跨实例并发写同一 `memoryId` 仍需上层保证串行；
2. **整段重写**：每次写入都可能覆盖整段 JSON，消息上限越大，写放大越明显；
3. **只按条数裁剪**：不感知 token 数，长消息场景下 `maxMessages` 不等于安全的上下文长度；
4. **实例缓存无过期**：Provider 的 Map 需要配合外部清理策略。

后续可以沿着三个方向扩展：

- **按 token 裁剪**：把 `maxMessages` 升级为 `maxTokens`，需要引入 token 估算；
- **批量写接口**：减少 `ReActAgent.initMessages` 中 `clear + 逐条 add` 带来的多次 Store 往返；
- **摘要记忆**：窗口满时先生成历史摘要，再保留最近消息，用同一套 `ChatMemory` 契约替换实现。

<br/>

## 七、总结

窗口会话记忆的实现可以压缩成三句话：

1. **自身不存状态**，所有消息读写都委托给 `ChatMemoryStore`；
2. **批量读、批量裁、批量写**，一次 `add` 只产生一次存储往返；
3. **裁剪只做两件特殊处理**：系统消息常驻、工具消息成组淘汰。

它验证了上一篇的分层设计：`ChatMemory` 负责策略，`ChatMemoryStore` 负责机制。窗口规则再复杂，也不会污染 ReAct 内核；存储介质再变化，也不需要重写裁剪逻辑。
