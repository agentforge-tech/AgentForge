# AgentForge 标准上传文件规范

> 文档定位：定义 `agentforge-service` 文件上传能力的设计基线、接口契约与首版本地存储实现。
>
> 落地模块：`agentforge-service/agentforge-service-web`
>
> 首版边界：单文件上传、本地磁盘存储、静态资源访问；暂不建设文件元数据表、鉴权下载、分片上传和对象存储。

---

## 1. 背景与目标

### 1.1 背景

AgentForge 的 Agent 对话、知识库、插件资源和图片生成等业务都会依赖文件能力。如果各业务自行处理文件名、目录、URL 和磁盘写入，将产生以下问题：

- 上传接口与返回结构不统一；
- 业务代码直接依赖本地磁盘，未来难以切换对象存储；
- 原始文件名冲突或携带路径，可能覆盖文件或导致目录穿越；
- 部署目录与开发目录不一致，配置容易散落；
- URL、物理路径和用户目录缺少统一约定。

因此，文件上传应作为 `agentforge-service` 的基础模块，先提供稳定、轻量的本地实现，再通过接口为后续 OSS、S3、MinIO 等存储方式预留扩展点。

### 1.2 设计思路

上传模块采用“HTTP 接入、存储抽象、本地实现、静态访问”的分层链路：

```text
FileController
    -> FileUploadService
        -> LocalFileUploadServiceImpl
            -> user.dir.upload
            -> /upload/** 静态资源映射
```

核心设计原则包括：

1. Controller 只维护 HTTP 契约，不直接写磁盘；
2. 使用上传服务接口隔离具体存储方式；
3. 物理目录与访问路径分别配置；
4. 服务启动时统一解析 `user.dir.upload`；
5. 返回访问地址、存储文件名、原始文件名、类型和大小。

AgentForge 首版不引入文件数据库表与删除/下载凭证逻辑。当前尚未建立文件生命周期和权限模型，过早落库会增加事务补偿和孤儿记录处理成本。

### 1.3 目标

1. 提供统一接口 `POST /api/file/upload`；
2. 默认写入 `agentforge-service/upload/`；
3. 所有文件按用户 ID 隔离存储；
4. 存储名全局随机，原始文件名只作为元信息返回；
5. 通过 `/upload/**` 直接访问本地文件；
6. 拒绝空文件与非法用户 ID，用户目录不由客户端传入；
7. 保持存储接口稳定，后续可增加对象存储实现。

### 1.4 非目标

首版不包含：

- 多文件、分片、断点续传和秒传；
- 文件元数据表、引用计数和自动清理；
- 文件内容安全扫描与图片转码；
- 私有文件鉴权、签名 URL 与下载审计；
- 前端上传组件；
- OSS、S3、MinIO 等远程存储实现。

## 2. 核心设计

### 2.1 总体链路

```text
multipart/form-data
       │
       ▼
FileController
       │  FileUploadService.upload(file, userId)
       ▼
LocalFileUploadServiceImpl
       ├── 校验文件和业务路径
       ├── 生成 UUID 存储名
       ├── 拼接 userId/UUID.ext
       ├── 校验最终路径仍在 upload 根目录内
       └── 写入本地磁盘并返回 UploadFileVo
                         │
                         ▼
UploadWebMvcConfiguration: /upload/** -> file:${user.dir.upload}/
```

### 2.2 代码职责

| 组件 | 职责 |
| --- | --- |
| `FileController` | 定义上传 HTTP 接口和参数，不处理磁盘细节 |
| `FileUploadService` | 稳定的文件存储抽象，隔离本地与远程实现 |
| `LocalFileUploadServiceImpl` | 校验、命名、目录生成、本地写入和结果组装 |
| `LocalUploadProperties` | 解析物理根目录、访问前缀并生成访问 URL |
| `UploadWebMvcConfiguration` | 将访问路径映射到本地上传目录 |
| `UploadFileVo` | 定义跨业务统一的上传响应 |
| `EnvironmentContext` | 集中读取上传目录、访问前缀等运行配置并统一默认值 |
| `SystemPropertyUtil` | 在 Spring 启动前解析服务主目录并设置 `user.dir.upload` |

### 2.3 核心接口

```java
public interface FileUploadService {

    UploadFileVo upload(MultipartFile file, Long userId);
}
```

`userId` 必须由后端当前用户上下文提供，禁止从请求参数接收，避免客户端跨用户写入文件。当前版本尚未接入登录态，统一使用默认用户 `1`；后续只需替换 Controller 中的当前用户获取逻辑。

首版只有一个 `FileUploadService` Bean，即 `LocalFileUploadServiceImpl`。未来增加对象存储时，应通过存储类型配置或工厂选择实现，Controller 契约和业务调用方无需变化。

### 2.4 目录与命名规范

文件最终存储结构：

```text
${user.dir.upload}/{userId}/{32位UUID}.{安全扩展名}
```

示例：

```text
agentforge-service/upload/1/ce6be7e12eb54f93bcac84034d3f852b.png
```

对应访问地址：

```text
http://127.0.0.1:8080/upload/1/ce6be7e12eb54f93bcac84034d3f852b.png
```

规则如下：

- 第一层目录固定为当前用户 ID，隔离不同用户的文件；
- 存储名使用 UUID，不使用原始文件名，避免重名覆盖和特殊字符问题；
- 扩展名转为小写，仅保留 1～16 位字母或数字；
- 原始文件名仅作为响应元信息，不参与路径拼接；
- 客户端不得传入目录或用户 ID；
- 返回可直接访问的完整 URL，协议、访问主机和端口由 `EnvironmentContext` 统一管理。

### 2.5 默认目录解析

`AgentForgeServiceApplication` 在创建 Spring 容器前调用：

```java
SystemPropertyUtil.setSystemUserDir();
```

其中 `setLocalUploadFileDir()` 会解析服务主目录，并设置：

```text
user.dir.upload=/绝对路径/agentforge-service/upload/
```

服务主目录探测顺序与 `user.dir.conf` 一致：

1. 当前工作目录包含 `conf/`：当前目录就是服务主目录；
2. 当前工作目录包含 `agentforge-service/conf/`：使用其下的 `agentforge-service/`；
3. 上级目录包含 `conf/`：使用上级目录；
4. 均未命中：回退到当前工作目录。

因此从仓库根目录、`agentforge-service` 目录或 IDE 启动时，均能得到稳定的默认上传目录。

## 3. HTTP 接口规范

### 3.1 上传文件

```http
POST /api/file/upload
Content-Type: multipart/form-data
```

请求参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `file` | MultipartFile | 是 | 待上传文件，不能为空 |

请求示例：

```bash
curl -X POST 'http://127.0.0.1:8080/api/file/upload' \
  -F 'file=@/tmp/demo.png'
```

成功响应：

```json
{
  "visitUrl": "http://127.0.0.1:8080/upload/1/ce6be7e12eb54f93bcac84034d3f852b.png",
  "fileName": "1/ce6be7e12eb54f93bcac84034d3f852b.png",
  "originFileName": "demo.png",
  "fileType": "png",
  "fileSize": 10240
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `visitUrl` | 浏览器或业务侧可直接使用的完整访问地址 |
| `fileName` | 相对上传根目录的存储路径，不能当作操作系统绝对路径 |
| `originFileName` | 清理路径信息后的原始文件名，仅用于展示 |
| `fileType` | 安全扩展名，不含点；无安全扩展名时为空字符串 |
| `fileSize` | 字节数 |

### 3.2 错误响应

上传业务异常由 `GlobalExceptionHandler` 转换为 HTTP 400。典型错误码：

| code | 场景 |
| --- | --- |
| `INVALID_UPLOAD_FILE` | 文件为空、业务路径非法或路径越界 |
| `FILE_UPLOAD_FAILED` | 创建目录或写入文件失败 |

示例：

```json
{
  "status": 400,
  "code": "INVALID_UPLOAD_FILE",
  "message": "Uploaded file must not be empty"
}
```

超过 Spring Multipart 限制的请求由框架在进入 Controller 前拒绝，不属于上述业务错误。

## 4. 配置规范

#### 4.1 上传模块配置

上传目录与访问前缀的配置 key 及默认值由 `EnvironmentContext` 单点维护：

```java
private static final String DEFAULT_UPLOAD_DIR = "./upload";
private static final String DEFAULT_UPLOAD_VISIT_PATH = "/upload";
private static final String DEFAULT_UPLOAD_VISIT_PROTOCOL = "http";
private static final String DEFAULT_UPLOAD_VISIT_HOST = "127.0.0.1";
private static final String DEFAULT_UPLOAD_MAX_SIZE = "10MB";

public String getFileLocalStoragePath() {
    return environment.getProperty("agentforge.file.local.storage-path", getUserDirUpload());
}

public String getFileLocalVisitPath() {
    return environment.getProperty(
            "agentforge.file.local.visit-path", DEFAULT_UPLOAD_VISIT_PATH);
}

public long getFileUploadMaxSize() {
    String configured =
            environment.getProperty("agentforge.file.max-size", DEFAULT_UPLOAD_MAX_SIZE);
    return DataSize.parse(configured).toBytes();
}
```

| `EnvironmentContext` 方法 | 配置 key | 默认值 |
| --- | --- | --- |
| `getFileLocalStoragePath()` | `agentforge.file.local.storage-path` | `getUserDirUpload()` |
| `getFileLocalVisitPath()` | `agentforge.file.local.visit-path` | `/upload` |
| `getFileLocalVisitProtocol()` | `agentforge.file.local.visit-protocol` | `http` |
| `getFileLocalVisitHost()` | `agentforge.file.local.visit-host` | `127.0.0.1` |
| `getUserDirUpload()` | `user.dir.upload` | `./upload` |
| `getFileUploadMaxSize()` | `agentforge.file.max-size` | `10MB` |
| `getServerPort()` | `server.port` | `8080` |

`user.dir.upload` 会在服务启动前由 `SystemPropertyUtil` 设置为 `agentforge-service/upload/` 的绝对路径；`./upload` 只是脱离标准启动入口时的保底值。

默认情况下无需在 `application.yml` 重复声明。需要覆盖时才增加：

```yaml
agentforge:
  file:
    max-size: 10MB
    local:
      storage-path: /data/agentforge/upload
      visit-protocol: https
      visit-host: agentforge.example.com
      visit-path: /upload-assets
```

#### 4.2 Multipart 大小限制

业务上传上限的配置 key 与 `10MB` 默认值由 `EnvironmentContext` 统一维护。`UploadWebMvcConfiguration` 基于该值创建 `MultipartConfigElement`，同时限制单文件大小和整个 multipart 请求大小，无需在 YAML 中重复声明。Agent 头像与 MCP/HTTP 插件图标的前端校验也统一为 `10MB`。

环境变量覆盖示例：

```bash
export AGENTFORGE_FILE_MAX_SIZE=10MB
```

生产环境可通过环境变量或 YAML 覆盖物理目录，例如：

```bash
export AGENTFORGE_FILE_LOCAL_STORAGE_PATH=/data/agentforge/upload
```

如果修改 `visit-path`，接口返回的 `visitUrl` 与 Spring 静态映射会同步变化。该路径禁止配置为 `/`，避免将本地目录映射到站点根路径。生产环境需将 `visit-protocol` 和 `visit-host` 配置为客户端可访问的外部协议与域名，`server.port` 参与完整 URL 拼接。

## 5. 具体落地实现

### 5.1 启动阶段

1. `SystemPropertyUtil` 解析 `agentforge-service` 服务主目录；
2. 设置 `user.dir.upload` 绝对路径；
3. Spring 读取 `application.yml`；
4. `EnvironmentContext` 统一解析配置项及默认值；
5. `LocalUploadProperties` 将存储路径转为绝对、规范化的 `Path`；
6. `UploadWebMvcConfiguration` 注册 `/upload/**` 静态资源处理器。

### 5.2 请求处理阶段

1. Controller 读取 `file` 并获取当前用户 ID（当前固定为 `1`）；
2. Service 拒绝 `null` 或空文件；
3. 去除原始文件名可能携带的客户端目录；
4. 提取并校验安全扩展名；
5. 校验用户 ID 为正整数；
6. 生成用户目录和 UUID 存储名；
7. 对最终路径执行 `normalize()`，并验证仍以存储根目录开头；
8. 创建父目录，通过流写入目标文件；
9. 组装统一 `UploadFileVo` 返回。

### 5.3 安全基线

首版实现必须遵守以下约束：

- 不允许客户端传入绝对物理路径；
- 不使用原始文件名作为目标文件名；
- 不接收客户端传入的 `path` 或 `userId`；
- 最终路径必须位于规范化后的上传根目录内；
- 静态资源映射仅绑定上传根目录，不映射服务主目录；
- 日志不得输出文件内容；
- 文件大小由 Spring Multipart 配置统一限制。

需要注意：静态 `/upload/**` 是公开访问能力，适合头像、图片、公开附件等资源。身份证明、密钥、私有知识库附件等敏感文件不得直接使用该公开链路。此类需求应新增鉴权下载接口或签名 URL，不应通过隐藏 URL 代替权限控制。

## 6. 业务接入规范

业务模块需要上传文件时，优先依赖 `FileUploadService`，不要：

- 自行拼接 `${user.dir.upload}`；
- 在 Controller 中调用 `MultipartFile.transferTo()`；
- 自行生成 `/upload/...` URL；
- 将操作系统绝对路径返回给前端；
- 复用用户原始文件名作为存储名。

服务内调用示例：

```java
UploadFileVo uploaded = fileUploadService.upload(file, currentUserId);
String avatarUrl = uploaded.getVisitUrl();
```

业务侧只持久化 `visitUrl`，不保存物理绝对路径。Agent 头像使用 `avatar` 字段，MCP/HTTP 插件图标使用 `icon` 字段，三者均复用统一上传接口。

## 7. 演进方向

### P1：文件治理

- 建立文件元数据表，记录存储类型、对象键、原始名、MIME、大小、摘要、创建人和状态；
- 增加统一删除接口和事务提交后的物理文件清理；
- 增加 MIME/文件头校验、扩展名白名单和恶意文件扫描；
- 为私有文件提供鉴权预览、下载和审计。

### P2：对象存储

- 增加 `S3FileUploadServiceImpl` 或 `OssFileUploadServiceImpl`；
- 将“本地/对象存储”的选择收敛到工厂或条件 Bean；
- `fileName` 演进为与实现无关的对象键；
- 保持 `POST /api/file/upload` 和 `UploadFileVo` 基本兼容。

### P3：大文件能力

- 分片上传与断点续传；
- 内容摘要去重和秒传；
- 临时分片过期清理；
- 上传完成事件与异步转码/解析任务。

---

## 8. 验收标准

1. 从仓库根目录或 `agentforge-service` 目录启动，默认文件均写入 `agentforge-service/upload/`；
2. 当前环境上传文件统一写入 `upload/1/`；
3. 返回的 `visitUrl` 可通过同一服务直接访问；
4. 同名文件多次上传不会互相覆盖；
5. 上传接口不接收客户端指定的目录或用户 ID；
6. 空文件和超过 `10MB` 的文件被拒绝，前后端限制保持一致；
7. 单元测试通过，`agentforge-service-web` 编译通过；
8. 配置模板、接口字段和实际实现保持一致。
